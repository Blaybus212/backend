# ADR 013: UserGrass 엔티티에 Streak 데이터 직접 저장

## Status
Accepted

## Context
사용자의 활동 기록(잔디)을 조회할 때 '연속 학습 횟수(Streak)'를 함께 보여주어야 한다.
초기 설계에서는 API 요청 시마다 과거 이력을 전수 조사하여 Streak을 계산하는 방식을 고려했으나, 다음과 같은 문제점이 예상되었다.

1. **계산 복잡도**: 서비스가 장기화될수록 한 사용자의 Streak을 계산하기 위해 조회해야 하는 데이터 양이 늘어날 수 있다.
2. **로직 가독성**: 과거 데이터를 순회하며 Gap을 찾는 로직이 복잡하여 유지보수가 어렵다.
3. **성능**: 매 요청마다 반복되는 집계 연산은 DB 및 서버 자원을 낭비한다.

## Decision
각 날짜의 활동 점수를 저장하는 `UserGrass` 엔티티에 해당 시점의 `streak` 값을 물리적으로 저장하기로 결정했다.

1. **UserGrass 필드 추가**: `Integer streak` 필드를 추가하여, 매일 활동이 기록(또는 업데이트)될 때 이전 날짜의 `streak`에 1을 더해 저장한다.
2. **조회 효율화**: 최신 Streak을 조회할 때 복잡한 루프 없이 오늘 또는 어제의 `UserGrass` 레코드 하나만 조회하면 즉시 값을 얻을 수 있다.
3. **데이터 정합성**: Streak 계산 로직은 데이터를 생성/변경하는 시점에 수행하며, 조회 시점에는 저장된 값을 신뢰한다.

## Consequences
- **장점**: API 응답 속도가 대폭 향상되고 비즈니스 로직이 단순해진다.
- **단점**: 과거 데이터가 수정되거나 누락된 데이터가 사후적으로 채워질 경우, 해당 날짜 이후의 모든 `streak` 값을 재계산(Cascade Update)해야 하는 부담이 있다. (단, 본 서비스의 성격상 과거 활동은 소급 적용하지 않는 것을 원칙으로 하여 이 위험을 최소화한다.)
