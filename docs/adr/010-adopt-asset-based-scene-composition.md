# ADR-010: 자산(Asset) 기반 장면 조립 및 설정 관리 전략 채택

## Status

Accepted

## Date

2026-02-09

## Context

학습 어시스턴트 기능인 `Simvex`에서는 학습의 최소 단위인 '부품(Component Asset)'과 이를 조립한 형태인 '장면(Scene)'이 존재합니다. 초기에는 하나의 거대한 단일 GLTF 파일을 사용하는 방식을 고려했으나, 다음과 같은 요구사항과 문제점을 해결해야 했습니다.

1.  **자산의 재사용성 및 라이브 참조**: 볼트, 너트와 같은 공용 부품들이 여러 장면에서 중복 사용됩니다. 부품 에셋 수정 시 이를 참조하는 모든 장면에 즉시 반영되는 **'라이브 참조(Live Reference)'** 방식을 통해 에셋 파이프라인의 유지보수 효율을 극대화하고자 했습니다.
2.  **데이터 정합성 및 일관성 (SSOT)**: 부품의 고유 정보(설명, 재질 등)는 모든 사용자에게 일관되게 보여야 합니다. 이를 위해 도형 정보와 메타데이터를 분리하여 DB를 정보의 원천(Single Source of Truth)으로 삼았습니다.
3.  **복합 변형 제어**: 부품의 단순 배치뿐만 아니라 전단(Skew)이나 비균일 스케일 등 복합적인 기하학적 변형을 엔진 레벨에서 지원하기 위해, PRS(Position, Rotation, Scale) 대신 **4x4 Matrix** 형태의 변환 정보를 채택했습니다. 이는 외부 엔진(Three.js 등)과의 데이터 호환성 측점에서도 유리합니다.
4.  **개인화 및 확장성**: 사용자마다 개별적으로 메모를 추가하거나, 특정 시나리오에서의 조립 상태를 저장할 수 있는 인터페이스가 필요했습니다.
5.  **컴퓨팅 리소스 전략**: 네트워크 대역폭과 서버 부하 사이의 균형을 위해, v1에서는 서버 사이드 조립을 수행하되 향후 클라이언트 사이드 조립으로 전환할 수 있는 유연한 데이터 구조가 필요했습니다.

## Decision

**우리는 불변하는 '도형 정보(Geometry Asset)'와 가변적인 '조립 정보(Assembly Config)'를 분리하고, DB를 정보의 원천(SSOT)으로 삼는 자산 기반 장면 조립 아키텍처를 채택하기로 결정했습니다.**

구체적인 설계 전략은 다음과 같습니다.

1.  **최소 단위의 에셋화 및 참조**: 부품을 독립적인 GLTF 파일로 관리하며, 장면 정의 시 이를 라이브 참조(Live Reference)하는 방식을 사용합니다.
2.  **4x4 Matrix 기반 변환 관리**: 모든 배치 정보는 16개의 요소를 가진 4x4 행렬로 관리하여 표현의 유연성과 수학적 정확성을 확보합니다.
3.  **서버 사이드 조립 엔진 (v1)**: 현재 버전에서는 Node.js(`gltf-transform`)를 백엔드에 통합하여 서버에서 조립된 단일 GLTF/GLB 결과물을 전송합니다. 이는 클라이언트 뷰어 구현의 복잡도를 낮추고 시각적 일관성을 즉각 확보하기 위함입니다.
4.  **클라이언트 사이드 조립 로드맵 (v2)**: 데이터 전송량 효율화를 위해, 향후 클라이언트가 각 에셋을 개별 캐싱하고 수신한 메타데이터(Matrix 정보)를 바탕으로 브라우저에서 직접 조립하는 방식(Edge Assembly)으로 전환할 수 있는 데이터 스키마를 유지합니다.

## Trade-off Analysis

### 1. 자산 기반 조립 방식 (선택됨)

**장점 (Pros):**

- **유지보수 용이성**: 원본 부품 에셋 하나만 수정하면 이를 사용하는 수만 개의 장면이 동시에 업데이트됩니다.
- **표현의 정교함**: 4x4 행렬 사용으로 단순 위치 이동을 넘어선 복합 기하학 모델링 수치를 정확히 전달할 수 있습니다.
- **메타데이터 확장성**: DB를 통해 부품 단위로 메모, 상태값 등을 동적으로 주입하거나 특정 부품 강조(Highlight) 인터랙션을 처리하기 쉽습니다.
- **로드맵 호환성**: 현재의 서버 조립 방식은 향후 클라이언트 사이드 조립으로 넘어가기 전의 중간 단계(Bridge)로서 설계되어, 클라이언트 캐싱 전략 도입이 용이합니다.

**단점 (Cons):**

- **운영 복잡도**: 서버에서 Node.js 런타임을 유지해야 하며, 조립 과정에서 CPU 연산 비용이 발생합니다.
- **참조 무결성 관리**: 원본 에셋 삭제 시 참조 중인 모든 장면이 파손될 위험이 있어 엄격한 리소스 생명주기 관리가 필요합니다.

### 2. 단일 거대 GLTF 방식 (기각됨)

**장점 (Pros):**

- **단순함**: 파일 하나만 로드하면 되므로 별도의 조립 로직이 필요 없습니다.

**단점 (Cons):**

- **중복 데이터**: 동일 부품이 여러 장면에 포함될 경우 전체 파일 크기가 기하급수적으로 증가합니다.
- **메타데이터 동기화의 어려움**: 부품 설명 수정 시 모든 GLTF 파일을 다시 익스포트해야 합니다.
- **인터랙션 제약**: 부품별 고유 ID 관리가 어려워 부품 단위의 정교한 인터랙션 구현이 복잡해집니다.

## Consequences

- 모델링 팀과의 협업 스펙이 '형상 에셋'과 '설정 파일(Config JSON)' 단위로 표준화됩니다.
- 부품과 장면의 관계를 관리하는 `Component`, `Alignment`, `SceneInformation` 테이블이 핵심 도메인 모델이 되며, 사용자별 환경값은 `UserScene`에서 관리되어 라이브 참조 중에도 개인화된 뷰를 제공합니다.
- 서버 환경은 조립 엔진 실행을 위한 멀티 런타임(Java/Node.js)으로 운영되며, 이는 클라이언트 사이드 조립으로 전환하기 전까지의 전략적 선택입니다.
- 운영 시 에셋의 삭제는 'Soft Delete' 또는 'Versioning'을 권장하여 장면의 파손을 방지합니다.
- 초기 데이터 로딩 구현체(`DataLoader`)를 통해 `assembly_config.json`을 파싱하여 DB를 초기화하는 구조가 정착되었습니다. 상세 스펙은 [Scene Assembly API 명세](../specs/scene/scene_assembly.md)를 참고합니다.
